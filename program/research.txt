What p-Memo changes
p-memo is basically the Memo program rewritten with Pinocchio. Its interface is still essentially:

instruction_data = UTF-8 message bytes
It doesn't maintain a chat account, session, buffer, stream, etc. It validates the UTF-8 memo and logs/stores the instruction data as part of the transaction. 

But it is much cheaper computationally. Published benchmarks put it around:

0 signers:   ~287 CU
1 signer:    ~513 CU
2 signers:   ~628 CU
3 signers:   ~743 CU
versus ~13.5k CU for a one-signer legacy Memo invocation. 

So something like:

Wallet A                           Wallet B

"e"        ───── tx 2 ─────────►
"l"        ───── tx 3 ─────────►
"l"        ───── tx 4 ─────────►
"o"        ───── tx 5 ─────────►
is technically possible.

But I would not do one transaction per character.

Normal Solana transaction submission is essentially:

Raiku is doing something materially closer to what you're imagining. Their architecture advertises ahead-of-time compute reservations and just-in-time execution, where blockspace can effectively be reserved or prioritized rather than relying purely on best-effort submission. 

Conceptually:

                         SLOT N
                    ┌───────────────┐
normal traffic ───► │               │
                    │ reserved area │ ◄── your stream
                    │               │
                    └───────────────┘
Their AOT model is essentially:

reserve execution capacity for some future slot

while their JIT model targets imminent execution. 

So your idea:

“Can I pay the validator for a buffer into which I continuously send messages?”

isn't literally a validator allocating you a mutable byte buffer.

But reserved blockspace / compute is very close to the execution primitive you'd want.

You could imagine reserving capacity such that:

slot N      message chunk 001
slot N+1    message chunk 002
slot N+2    message chunk 003
slot N+3    message chunk 004
...
and having extremely predictable inclusion.

Rakurai is related but somewhat different. Its current docs describe a specialized scheduler, transaction inclusion infrastructure, tips, private transaction flows and validator-side scheduling optimizations.

Rather than making p-Memo itself the protocol, I would build a tiny messaging program with p-Memo-like efficiency.

    conversation_id: [u8; 16],
    sequence: u32,
    flags: u8,
    payload: [u8],
